coaching, and how the two should stay in sync so nothing gets missed.

================================================================================

    daily_logs, food_entries, exercises, workout_sessions, exercise_sets,

  * Actions (v3): summary, set_target, log_weight, add_note, log_food,
    log_workout, void_food_entry, version, send_message, list_messages.
  * summary returns: profile, weights (90d), intake (30d, full macros),
    workouts (20 sessions w/ sets), currentTarget, targetHistory (10).

    scan + USDA/OFF search + per-label manual entry + fast log), Recipes
    (create/publish/portion), Training (workout logging), Body (weigh-ins),
    Coach, Profile (settings + Muse token).
  * Per-user background/accent theme (admin-set via profiles.theme_color).
  * Live at https://adonis-a3y.pages.dev

Domain logic (src/domain, pure/tested):
  * Adaptive expenditure engine (estimates TDEE from weight trend vs intake).
  * Target calculator, recipe portioning, EWMA weight trend + stall detection.

PART 2 — GAPS THAT LIMIT ADVICE QUALITY (prioritized)
================================================================================
These are the things Muse currently CANNOT see/do that would materially improve
its coaching. Ordered by impact on advice quality.

  G1. [SHIPPED v3] targetHistory (last 10) now in `summary`. Expenditure estimate
      series still not exposed — see "Remaining" below.

  G2. [SHIPPED v3] intake now carries carbs + fat (full macros) per day.
      Fiber/micros still not included — see "Remaining" below.

  G3. No pre-computed trend/stall/adherence signal.
      The app computes weight slope + isStalled internally but doesn't expose it.
      Muse re-derives it (or misses it).
      FIX: add to `summary`: current weight slope (kg/wk), days-stalled flag,
      and logging adherence (days logged / days elapsed).

  G4. Body measurements trend not in context.
      Weights are present; waist/body-fat trend matters for recomp advice.
      FIX: include measurement series (already partially there via weights;
      extend to waist/bodyfat over time).

  G5. Muse Inbox is write-only from Muse's side.
      Muse can add_note but can't read back / mark processed.
      FIX: add `list_notes` and `mark_note` actions (optional, lower priority).

  G6. No cycle awareness in the API.
      Cycles (cut/maintain/bulk phases) exist in the schema but Muse can't read
      or manage them via the function.
      FIX: include active cycle in `summary`; optionally a `set_cycle` action.

PART 3 — HOW COPILOT (dev) AND MUSE (coach) STAY IN SYNC
================================================================================
The risk: each works from partial info and something gets missed. The fix is a
single source of truth + a lightweight change protocol.

  R1. SINGLE SOURCE OF TRUTH = this repo.
      * MUSE_API.txt  = the live API contract (what Muse may call).
      * This file     = state + gaps + plan.
      * PLAN.md       = product vision / decisions.
      Rule: if the API changes, MUSE_API.txt is updated IN THE SAME COMMIT.
      Muse should treat MUSE_API.txt as authoritative, not memory.

  R2. VERSION THE CONTRACT.
      * Add a "contract_version" to MUSE_API.txt and bump it on any change.
      * Muse can call a tiny `ping`/`version` read to confirm it's using the
        current contract before relying on new fields.

  R3. CHANGE LOG SECTION (below, Part 4).
      * Every API/behavior change gets a dated line. Muse reads the top of the
        log to learn what's new since it last checked.

  R4. CAPABILITY NEGOTIATION.
      * If Muse needs something it can't do (e.g. "I want fiber per day"), it
        records it as a request — either via `add_note` with a prefix like
        "CAPABILITY-REQUEST: ..." or by telling the user, who relays it here.
      * Copilot reviews these and either adds the capability or explains why not.

  R5. NO BLIND WRITES.
      * Muse only writes via the documented actions and only after a `summary`
        read. This prevents junk rows and keeps the data clean.

  R6. PERIODIC RE-SYNC.
      * Each coaching session starts with `summary` + a glance at the change log
        version, so Muse always works from current state + current contract.
